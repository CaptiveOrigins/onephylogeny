# Changelog

## Unreleased

- **Sanger chromatograms (roadmap stage 6.3):** `readAbif` reads ABI `.ab1` files: called bases, Phred qualities, peak positions, the four traces and the sample name. On two of Biopython's test files it reads the same bases, qualities and sample names Biopython does. A file that isn't ABIF, is cut short or has no base calls is refused with a plain reason. `assessRead` trims by Mott's algorithm (the Phred and Biopython method), turns kept bases below Q20 into N, flags positions with a strong second peak (a mixed sample, a nuclear copy or heteroplasmy; calls are unchanged), and rates the read usable, short or failed. A read without quality values is failed, never trusted. The thresholds (cutoff 0.05, Q20, 100 bases, a second peak a third of the first) are stated defaults, not calibrated. CLI: `onephylogeny sanger --ab1 FILE`.
- **Primer-to-window check (roadmap stage 6.3):** `checkPrimers` places a primer pair on the panel's reference (IUPAC codes allowed, up to 3 mismatches) and says which windows the amplicon covers whole, in part or not at all. Bases under the primers come from the primers, so they're left out of what the sample can tell. Primers that sit outside the marker are placed on a longer reference with the marker's offset. A primer found nowhere, or in two equally good places, is a refusal. CLI: `onephylogeny primers --dir PANEL --forward SEQ --reverse SEQ`.

## 0.1.0-alpha.7

Publishes on npm the work the Mac app 0.3.0 already carries, described in full under "Mac app 0.3.0" below: the region map (`RegionMap`, ecoregion tags on groups, ADR 0008), the haplotype network (`haplotypeNetwork`, `HaplotypeNetworkFigure`), chimera candidates (`chimeraCandidates`, `onephylogeny chimeras`) and sample QC (`result.qc`, with uncalibrated default thresholds). Results for the same panel and sequence keep their statuses; QC and conflicts are reported beside them.

## Mac app 0.3.0

The Mac app at OnePhylogeny 0.1.0-alpha.6 and the unreleased work below it: stage 3's Study-tab paper lookup and guided setup ("Suggest a reference"), curation history on every decision, sample QC in results, and the haplotype network in the Panel tab. The README now gives both ways past macOS's warning. A person hasn't yet worked through this build; that is test T26.

- **Region map (roadmap stage 5, ADR 0008, owner 2026-11-10):** panel groups can carry `ecoregions` (RESOLVE Ecoregions 2017 IDs), validated and sealed, and `RegionMap` in the React package shades them by group, with neighbouring ecoregions for context, a legend, a table and the credit line. `scripts/ecoregions.mjs` builds the outlines from the official release, simplified to about 8 MB, with mapshaper (not a dependency). Rendered by hand with illustrative tags for the redfoot groups; no real panel is tagged yet.
- **Haplotype network (roadmap stage 5):** `haplotypeNetwork(panel, window)` in core, `HaplotypeNetworkFigure` in the React package, and a section in the Mac app's Panel tab with a window chooser.
  - It's a minimum spanning network of one window's haplotypes, from records covering it whole (ADR 0007), keeping every equally short link.
  - Circle area counts records, slices show groups in the validated categorical palette, and multi-step links are labelled.
  - It has a legend, hover titles, and a table with the same numbers. The deterministic layout is fitted so no circle is cut off.
  - The caption says it isn't a tree and that counts aren't population frequencies.
  - On the redfoot panel 0.7.1's 3p window: 24 haplotypes and 24 links, with 11 partial records left out.
- **Chimera candidates (roadmap stage 4):** `chimeraCandidates(panel)` in core and `onephylogeny chimeras --dir PANEL`. These are records whose windows are nearest to different groups' consensus: possible chimeras, or reads from two animals joined. It uses only records covering two or more windows whole (ADR 0007), compares against a consensus that leaves the record out so one odd record can't pull its neighbours, and counts a window only where the record's own group has something to compare. Candidates are flagged, never removed. On the redfoot panel 0.7.1 it can check none: no record covers the 5p window whole.
- **Sample QC (roadmap stage 4):** every result now carries `qc`: five named rules (missing data, mixed sites, frame, stops, clustered differences against the nearest panel record), each good, mediocre or bad, and an overall status. QC describes the sequence and changes no status. A panel can seal its own thresholds (`qc` in its settings); otherwise OnePhylogeny's stated defaults apply, which are proposals, not calibrated. Reports gain a "Sequence quality" section, and the result schema is regenerated. On the redfoot panel 0.7.1, all its member examples rate good, and verify still passes.
## 0.1.0-alpha.6

Roadmap stage 3 (making curation humane) is complete, along with the first parts of stages 4 and 5.

- **Payload, sweep:** `Evaluate` may return `{ skip: reason }` for a panel that can't be used right now. Its sequences stay waiting, and `assignWaiting` returns `skipped` and `skippedPanels`, so a run can report it. Agreed with the platform, for checking a panel's examples before use.
- **Panel methods text (roadmap stage 5):** `panelMethods(panel)` in core and `onephylogeny methods --dir PANEL`. It writes plain prose for a report's methods section, with the citation list, generated only from what the sealed panel records: taxa, marker, reference, record checks, nuclear-copy screen, windows, the evaluation rules (stated as configured values), validated claims by basis, limits and software. It never writes coordinates.
- **Conflict reporting (roadmap stage 4):** `resultConflicts(result)` in core, and a "Conflicting evidence" section in sample reports. It reports when more than one group fits, when different windows are closest to different groups (by differences per shared column), and when a comparison favours a ruled-out group or goes against the one that fits. Statuses are unchanged; conflicts are reported beside them. On the 8 saved redfoot results, 4 of the 5 that fit no single group show their 3p window closest to West Colombia / Panama and their 5p window closest to East Colombia / West Venezuela. Why isn't known: it could be the records, the groups or real mixing.
- **Guided setup (roadmap stage 3):** "Suggest a reference" in the Mac app's Setup, and `suggestReference` in acquire. It finds the nearest RefSeq complete mitochondrial genome, from the taxon itself or up to three levels above, and says when it had to use a relative. It also gives the taxon's mitochondrial genetic code from NCBI Taxonomy, offering only codes the frame check supports and saying why when it can't. Nothing is set until "Use …" is clicked. For redfoot (taxon 50047) it suggests NC_080265.1 with the vertebrate mitochondrial code, the same choices the hand-built profile made.
- **Mac app, paper lookup:** selecting a paper in the Study tab shows its DOI and PMID, with where they came from. For a study without them, "Find the published paper" lists proposals from Crossref and Europe PMC, with the title match and an open-access supplements link. If a source fails, the app says the list may be incomplete. Nothing is attached until "Use this link". The Study then records the link's source and approval time (`StudyPaper.linkSource`, `linkPaper` in core) and logs it. Crossref is added to the app's allowed hosts. Lookups share one paced connection, at most a request a second.
- **Paper lookup (roadmap stage 3):** `lookupPaper` in acquire and `onephylogeny lookup --title T [--authors A]` propose DOI and PubMed links for a study known only by its GenBank title, from Crossref and Europe PMC. Each proposal carries its service, how well the title matched and when it was retrieved, plus a link to the supplement list for open-access papers. `approveLink` attaches a link only when a person approves it, recording who and when, and never overwrites an existing DOI or PMID. Requests are paced one at a time, a second apart, with a User-Agent naming the tool and no personal email. A service that refuses is reported, not retried. Tried once each on a real redfoot study: Crossref found the 2010 paper's DOI.
- **Group audit decision (ADR 0007, owner 2026-11-10):** the audit stays strict, and the redfoot 5p gap is a stated limit.
- **Group audit (roadmap stage 3):** `auditGroups(panel)` in core and `onephylogeny audit --dir PANEL`. For each window, using only records that cover it whole, it reports each group's records, haplotypes and widest p-distance. It flags records closer to another group than to their own, haplotypes shared by two groups, and groups with a single record. It flags and never assigns. On the redfoot panel 0.7.1: the 3p window is clean (no misfits, no shared haplotypes). In the 5p window no record covers all 435 columns (the most complete has 433), so it can say nothing there, including about Brazil east. Whether to allow a little missing data is an open method question; the rule was not changed after seeing this.
- **Curation history (roadmap stage 3):** every saved change to a curation is appended to `curation-history.jsonl` beside it, field by field, from and to, with when, who (optional) and why. The Mac app and the CLI both save through `saveCuration`, so nothing skips the history. `curation import --apply` now needs `--reason`. `onephylogeny curation history [--record ID]` reads it back and reports any damaged line rather than skipping it.
- **Curation sheet (roadmap stage 3, bulk tools):** `onephylogeny curation export` prints every record of the latest run as a CSV, with its decision and read-only context (organism, length, title) and never a coordinate. `curation import --file F` checks a filled-in sheet and lists every change, and `--apply` saves it. A blank cell clears a field, a missing column or row keeps what was there, and any error refuses the whole sheet: an unknown group, class or use, a duplicate, an origin-reported record without its source, or coordinates in a site or note. Formulas are defused on the way out and restored on the way in. In core: `curationToCsv`, `curationFromCsv`, `parseCsv`, `bulkAssign` and `recordsOfStudy`, and in the engine `loadRunRecords`. Tried on the real redfoot curation: 296 records round-trip with no change, and a wrong group is refused.
## 0.1.0-alpha.5

Roadmap stage 2 is complete: panels are datasets that prove themselves.

- **Dataset README and citations:** `onephylogeny dataset` and every build also write `README.md` (groups, limits, how to check a copy, what to cite), and `dataset.json` names the software that built it and the panel's citations.
- **Sample routing (roadmap stage 2):** `routeSample(sequence, panels)` and `onephylogeny route --fasta FILE --panels DIR` suggest which installed panels apply to each sequence. Each panel's own reference and record checks decide, the same ones a test runs first, so a suggested panel accepts the sequence. Each suggestion says why it does or doesn't apply. Superseded panels, other markers, fragments outside every window and a taxon claim the panel isn't for are refused. The order is: applies, then active before candidate, more windows, more columns, newest version. It only suggests, and a person chooses. Panels in older formats are listed as skipped, never used. Tried on the redfoot panels: real cytb records route to them, and a random sequence routes to none.
- **Sample reports (roadmap stage 2):** `sampleReport(panel, result)` and `reportMarkdown` in core, and `onephylogeny report --dir PANEL --result FILE [--json]`. A self-contained report for one sample, built from the panel and result files alone: the conclusion, each group's status and reason, the comparisons between groups, coverage, gaps and caveats, versions and sources. A region is named only where the region card would name it, in the card's words, with its label and caveat. Otherwise the report says in plain words why no region is named. It never shows a coordinate. Tried on the 8 saved redfoot results: 3 name a region, 5 fit no single group, and none shows a position.
- **Published JSON Schemas (roadmap stage 2):** profile, curation, panel and result in `@captiveorigins/onephylogeny-core/schemas/`, and examples and dataset manifest in `@captiveorigins/onephylogeny-engine/schemas/`. They are generated from the TypeScript types by `pnpm schemas`, and a test fails if they drift. Each has a URN `$id` naming the format and version, such as `urn:onephylogeny:schema:panel:v2`. Unknown fields are refused, so a coordinate can't slip into a panel unnoticed. Everything the engine writes validates, and so do the real redfoot profile, curation, panel 0.7.1, its examples and manifest, and 8 saved results.
- **Panels prove themselves (roadmap stage 2, ADR 0006):** a built panel's folder now holds `examples.json` and `dataset.json`. The examples are, per group, the longest located member, a 300-base fragment and a control that must be refused, each with the answers it gave at build time. The manifest holds the SHA-256 of every file. `onephylogeny verify --dir DIR` checks the hashes and the seal, then reruns the examples, so a copy on another machine or under another software version is shown to give the same answers. `onephylogeny dataset --dir DIR` adds both files to a panel built earlier. Tested on made-up data, and on a copy of the real redfoot panel 0.7.1: 7 examples, about 0.3 s, and a one-base edit is caught.
- CLI: a failed save now removes its temporary file. The file store moved to `src/store.ts` and has its first tests: saves replace a file whole, a failed write keeps the old file, and nothing is left behind.

## 0.1.0-alpha.4

- **Payload, fixes access:** a result's site (the host's tenant field) could change after it was made. Someone who reviews one site and belongs to another could approve a result and then move it, so the other site's people would see it. Results, samples and sequences now keep the site they were made for. The new option `tenantField` names the field (default `tenant`). Tested with made-up reviewers on two sites.
- Tests: a reviewer can't make results, approving in bulk reaches only the reviewer's own site, and samples and sequences are read only by their own site's staff. First test audit in `docs/test-audit.md`.

## 0.1.0-alpha.3

- **Payload, fixes access:** an access rule that returns a query, such as "results on this reviewer's own site", was read as "everything" when it decided who sees pending results, panels, samples and sequences. Rules are now joined with "or" (`either`, `anyOf`, both exported), so a reviewer of one site sees and approves only that site's results. Tested with reviewers on two made-up sites.
- Payload: a result's links (animal, sequence, panel, import run) are checked when it is made and not again on review, since they can't change. A site's reviewer who can't read a private animal can still approve its result.

## 0.1.0-alpha.2

- Payload: optional `samples` and `sequences` collections (`records` option). `registerSequence` records one lab file as a sample and a sequence. It checks the file's text against its SHA-256 and refuses, in plain words, a file that isn't exactly one usable DNA sequence for its marker. One sample per kit; the same file again changes nothing, and a different file for the same kit is a second sequence on the same sample. `assignWaiting` tests waiting sequences against the panel for their marker and species and records results pending review, stamped with the panel's status. Tested with made-up data in an in-memory database.
- The region card uses the owner's confirmed wording: "Closer to the maternal line population sampled in <regions> than those in <others>. Other regions are unsampled or untested. Not proof of where this animal was collected."

## 0.1.0-alpha.1

- Hold-out reports add `byStatus`, how many findings had each status and how many concerned the true group, and `singleMatch`, how often one clear match was right, by tests and by sites, with an interval from 4 sites. No probabilities.
- Invariant P30 and `regionCard`: a result may name the region where the matched group's located records were sampled, and the regions it was found closer than, as a hypothesis about the maternal line. Draft card text, waiting for the owner's exact words: "Closer to the maternal line sampled in <regions> than to those sampled in <others>. Other regions are unsampled or untested. Not proof of where this animal was collected." `<others>` names only groups a validated comparison resolved against the match; a comparison favoring another group, or none resolved, shows nothing. It also shows nothing for an ambiguous, novel or out-of-scope match, or for records assigned by sequence. Regions are names, never coordinates. Public display needs the keeper's opt-in. A `candidate` panel shows regions only if a maintainer chose to show it, and `madeAgainst` keeps a result made against a candidate labeled exploratory. Hosts pass translated text and a `locale`, and region lists read naturally in that language ("A, B and C"). The card also comes back in `parts` (label, match, caveat), so a page can show the label as a badge and the caveat on its own line.
- Payload: panels gain `shownAsExploratory`, which only a candidate can have and which clears when it moves on. The new option `resultsAgainst: 'activeOrShown'` lets results be made against such candidates, and lets readers see them; the default stays `active`. Results stamp `panelStatus` and `panelShownAsExploratory` when made, and neither can change.
- **Payload, breaking for scripts that activate panels:** activating a panel needs a signed-in user, and the panel records who (`activatedBy`, their user ID) and when (`activatedAt`). Both are read-only and can't be set or changed any other way. A script without a user can still create candidates, but a person activates them. This records who pressed Activate, not who reviewed the panel's science.

## Mac app 0.2.0

The Mac app ships everything in this section. The npm packages aren't published yet.

- The Mac app no longer offers update checks. Releases have no signing key yet, so there is nothing to check; download the new DMG instead. Signed updates can return in a later release.
- A long record that doesn't annotate the marker, such as a whole mitochondrial genome, now has it cut out by similarity and then goes through the usual checks. It's refused if the marker looks present in more than one place. A record that was left whole used to skip the coverage check.
- Compare any two built panel versions in the Study tab, or with `onephylogeny compare --a V --b V`: records, groups, every evidence field, settings and full claim reports. It reports differences and never recommends a version.
- Duplicate a Study. A copy keeps the runs it came from, so later omissions in it are still labeled post hoc.
- Studies with post hoc omissions offer a copy with them restored, and panels seal the Study state they came from, including those omissions.
- **Breaking for panels:** panels now seal their record checks and a hash of their sequences. Earlier panels load as outdated and need a new version.
- Records assigned by their own sequence no longer shape a group's sites, spread, findings or validation. One such record could previously erase a fixed site and turn an exclusion into `consistent`.
- New provenance class `origin-reported`, which must name its source.
- Loading a panel verifies its seal, and a changed panel is refused.
- Unannotated records now get the coverage check unless they're many times the reference's length.
- New error `terminal-discordance` for foreign tails. Frame-shifting indels and in-frame stops now exclude records from panels, and still warn on samples.
- Analysis protocol: all results so far are exploratory, and rules are fixed before tests.
- NUMT screen (`scripts/numt-screen.mjs`): searches a related genome for nuclear copies of a marker and flags records closer to a copy than to the reference. It runs outside the app and needs BLAST+.
- **Breaking for panels and results:** schema version 2. Evaluation compares groups in pairs, within named windows. Earlier panels load as outdated.
- Results report `pairs` (`resolved`, `not_resolved` or `not_evaluable`), `candidatesNotEvaluated`, `novelty` and `outOfValidatedScope`. `novel_or_unsampled_flag` is gone from findings.
- `rules` replace `thresholds`: shared columns, records per column, sampling sites to rule a group out, decisive sites and tolerance. Windows can be set in the Panel tab.
- Group spread is per window and scales with the columns compared. `compatibility` now requires its minimum overlap.
- Loading a panel derives its sites again and refuses a mismatch.
- Validation harness: claims per pair and window, tested for sites, wrong answers, an exact interval on sites, agreement across studies, shuffled labels, a no-structure simulation and a minimum length. See `fullValidation`.
- **Breaking for profiles:** written `validatedScope` is ignored. Panels gain `claims`, and Payload refuses to activate a panel with no validated claims.
- Hold-out reports add record, haplotype and study schemes, and every row reports sites beside records.
- Mac app: a crash in a tab now shows the error instead of a blank window, and other failures appear in the error banner. Long panel builds show elapsed time beside the button, and opening a profile says it's loading. The clock keeps counting across tabs, only one job runs at a time, and setting provenance for a study shows what it's doing and what's now set.
- React: `ClaimsView`, and `ValidationView` shows the ladder and claims.
- React: `PairTable`, and the panel and validation views show pairs, records still needed and the stricter "all others compared" count.
- React: `TreeCanvas`, with pan, zoom, Fit, Download SVG and Print, plus the suite's shared `icons`. `TreeFigure` stays server-renderable.
- Mac app: the tree uses the canvas. Download saves `tree.svg` to the profile's exports, and Print opens the system dialog.
- Playground: every view on invented data (`apps/playground`).
- Release workflow for npm, not used yet.
